# BCI — Bannerlord Compatibility Intelligence

**Подготовленная версия исходников: 0.5.2-alpha (не опубликована) · Последний публичный релиз GitHub: 0.3.1-alpha · Windows 10/11 x64 · local-first**

BCI — локальное приложение для инвентаризации модов Mount & Blade II: Bannerlord, статического анализа их взаимодействий, построения рекомендаций по порядку загрузки и накопления подтверждённых результатов игровых тестов для последующего обучения модели.

## Установка для пользователя

Для обычного пользователя основной способ установки — **один Windows x64 Setup.exe**. Он устанавливает BCI в выбранную папку (по умолчанию `Program Files\BCI`), создаёт ярлык в меню «Пуск», по выбору — на рабочем столе, и устанавливает Microsoft Visual C++ Runtime, только если установленная x64-версия старее включённой или отсутствует. Python, pip, PyInstaller и Inno Setup пользователю устанавливать не требуется: Python и библиотеки включены в приложение.

После установки BCI автоматически запускается; в дальнейшем её можно открыть из меню «Пуск» или с рабочего стола. Укажи корневую папку Bannerlord — каталог, внутри которого находятся `Modules` и `bin` — и нажми «Проверить моды».

Переносимая сборка `BCI_Portable_<version>.zip` остаётся дополнительным вариантом. Для неё не предоставляется автоматическая установка обновлений: скачивай следующую portable-версию вручную. Для основной установленной версии обновления предлагаются из официального GitHub Releases через вкладку «Обновления».

> В этой рабочей среде подготовлены исходники и Windows CI workflow. Настоящий Windows `Setup.exe` должен быть собран Windows Runner GitHub Actions; Linux-сборка не выдаёт настоящий Windows PE-файл. До прохождения Windows CI и проверки установки на чистой Windows нельзя считать установщик проверенным.


## Текущие изменения 0.5.2-alpha (подготовка обновлений)

Добавлен раздел «Обновления». Установленная версия BCI проверяет официальный репозиторий `VoodyWoodman/BCI` через GitHub Releases, поддерживает каналы Stable и Preview, показывает описание релиза, скачивает установщик, сверяет размер и SHA-256 с `release-manifest.json`, а затем запускает Inno Setup с запросом UAC. Установка выполняется только после явного действия пользователя; сама программа не заменяет файлы внутри `Program Files`.

Автоматическая проверка выполняется при запуске не чаще одного раза в 24 часа и может быть отключена. При отсутствии сети BCI продолжает работать. Пользовательские данные, SQLite, отчёты, контрольные сборки и модели остаются в `%LOCALAPPDATA%\BCI` и не удаляются при обновлении или деинсталляции.

Первый переход с 0.5.1-alpha на 0.5.2-alpha потребует ручной установки нового Setup.exe, поскольку старая версия ещё не содержит Update Manager. После установки 0.5.2 следующие релизы смогут обновляться через вкладку «Обновления».

**Ограничение доверия:** SHA-256 проверяет целостность загруженного установщика относительно манифеста того же GitHub Release и HTTPS защищает передачу. Пока релизы не подписываются Authenticode-сертификатом; компрометация учётной записи/репозитория GitHub не устраняется одной контрольной суммой. Подписание Windows-приложения — отдельный шаг перед стабильным публичным выпуском.


## Предыдущий этап 0.5.1-alpha

BCI 0.5.1-alpha продолжает развитие собственного Load Order Engine. Текущий список Vortex/Launcher не используется как tie-breaker для сортировки: он нужен только для подтверждения состава профиля и последующего аудита нарушений.

Версионная проверка следует семантике BUTR ModuleManager. Одиночная версия и wildcard-версия задают минимальное требование; `ApplicationVersionRange` и NuGet-интервалы задают нижнюю и верхнюю границы. Если установленная версия выше минимальной и удовлетворяет диапазону, но строка отличается, BCI показывает информационное замечание с нулевым риском, а не объявляет мод несовместимым.

Поддержан JSON порядка Bannerlord для Vortex/BUTR. BCI берёт `isSelected` как включение, `isDisabled` — только как блокировку переключения, `index` — только для аудита. Файлы профилей расширения Bannerlord для Vortex автоматически ищутся в `%APPDATA%\Vortex\mountandblade2bannerlord\mods\<profileId>_loadorder.json` и `..._loadorder_multiplayer.json`. Свежий full-state snapshot Vortex имеет приоритет и подтверждает ID/режим профиля; если снимка нет, BCI может выбрать только однозначный самый свежий профильный JSON (не старше 30 минут), помечая выбор как предположительный. При неоднозначности BCI не угадывает. Остаточные настройки BEM не перекрывают обнаруженный профиль Vortex. Основное состояние Vortex хранится внутри самого приложения, поэтому BCI не читает его внутреннюю базу LevelDB напрямую.

В подтверждённом Singleplayer профиле сетевые/серверные официальные модули не включаются в граф и покрытие пар, если профиль явно не отмечает их включёнными. При неизвестном режиме BCI не угадывает. Отсутствие активного порядка в интерфейсе, HTML и TXT теперь отдельно отображается как «Не проверено», а не как ноль нарушений.

XML-сопоставление использует устойчивые ключи дочерних элементов (`id`, `skill_id`, `key`, `name`, `slot`, `type`) вместо позиционных индексов, когда эти ключи есть. Для пары с объявленной обязательной зависимостью BCI учитывает направление как кандидат штатного переопределения дополнения. Третий модуль помечается только кандидатом compatibility patch при наличии зависимостей от обоих модов и пересечения тех же спорных объектов. Это эвристическая классификация, не подтверждение функциональной совместимости.

Добавлен постоянный SQLite-кеш SHA-256 по пути, размеру и времени изменения файла. Повторные неизменённые файлы не читаются заново; чекбокс «Полная перепроверка файлов (без кеша)» принудительно пересчитывает хеши. Существующие записи сканов и обученные модели не удаляются.

Автотесты текущей рабочей копии 0.5.2-alpha: 117 pytest и 79 unittest прошли на Linux/Python 3.13.5. Импорт Tkinter и модулей приложения проходит. Реальный Windows UI, выполнение GitHub Actions, компиляция Inno Setup и установка/обновление на пользовательской Windows пока не проверены; публичный релиз 0.5.2-alpha не создан.


### Исправления качества 0.5.1-alpha

Ручной выбор JSON профиля Vortex — рекомендуемый и приоритетный источник. Автоматический поиск снимков полного состояния Vortex остаётся best-effort fallback и принимает только файлы с `mtime` не старше 30 минут. UI и HTML-отчёт показывают проверенные пути и причины принятия/отклонения кандидатов, имя/ID/режим профиля, а также точное время файла. Для обычного BUTR JSON имя профиля может отсутствовать; BCI явно сообщает об этом вместо догадки. `mtime` не следует считать гарантированным временем создания резервной копии.

Необязательные версионные требования `optional=true` не создают Medium-риск: несоответствие отражается как информационное замечание с 0 баллов. Эквивалентные требования из `DependedModules` и `DependedModuleMetadata` объединяются с сохранением источников доказательств; разные ограничения не объединяются. Служебные файлы `__folder_managed_by_vortex` исключены из анализа пересекающихся ресурсов.

Автоматические тесты: 85 pytest и 47 unittest. Реальный Windows UI/Vortex профиль, повторный скан для проверки hit rate SHA-256 кеша и Windows-установщик ещё не проверены.

## Предыдущий этап 0.4.0-alpha (локальная разработка)

Эта версия ещё не опубликована. В доступном архиве исходников BCI научился сопоставлять выбранную папку Bannerlord с отдельным экземпляром BEM и читать его собственный `LauncherData.xml`. Архив не содержит Git-метаданных, поэтому его точное соответствие ветке/коммиту GitHub нужно подтвердить отдельно. Сохранённые именованные JSON-профили BEM не используются как доказательство текущего активного порядка.

BCI отдельно показывает подтверждённое, частичное и неизвестное состояние активности модов. Моды с неизвестным состоянием включаются в статический анализ консервативно, но не обозначаются как достоверно включённые. Новая строка состояния в интерфейсе сообщает полноту найденного профиля. Эти изменения пока проверены автоматическими тестами и моделируемой структурой BEM; интеграционный запуск на реальной Windows-установке BEM ещё требуется.

Интерфейс получил более простые подписи, основное действие «Проверить моды», понятные пояснения и скрытый по умолчанию технический журнал прогресса. Стек Tkinter и локальная модель хранения не менялись.

В BCI добавлен собственный движок рекомендаций порядка. Он строит топологические группы по зависимостям и объявленным правилам модов; текущая последовательность Launcher/Vortex используется только для аудита нарушений и отображения исходных позиций, но не влияет на собственную сортировку BCI. Модули в одной группе не имеют доказанного взаимного приоритета по найденным метаданным.

Отчёт показывает покрытие попарного порядка: какой процент пар модов имеет взаимную позицию, выводимую из графа правил. Это метрика полноты доказательств порядка, а не шанс успешного запуска. Пересечения XML-объектов и ресурсов связываются с парами модов; если по файлам нельзя установить желаемое направление перезаписи, BCI не придумывает его и рекомендует тестировать оба варианта.

Во вкладке «Порядок загрузки» доступен экспорт текстового списка по группам с причинами и предупреждениями. Это инструкция для ручной перестановки в Vortex, а не нативный импортный файл Vortex; BCI не изменяет профиль или порядок в Vortex.

В анализе порядка загрузки добавлена защита от повторяющихся `Module ID`: все папки остаются видимыми, ссылки на дубли не разрешаются случайно, а применение рекомендации блокируется до устранения неоднозначности. Проверяются точные требования `DependentVersion` и версионные шаблоны BLSE в `DependedModuleMetadata`. Несовпадение версии показывается как предупреждение, а не автоматический диагноз вылета. Результат сортировки получает явный статус: готовая рекомендация, готовая с предупреждениями, предварительная или заблокированная. Даже статус `ready` означает только, что порядок построен по подтверждённому профилю и графу без критических неоднозначностей; BCI не записывает его в BEM/Launcher.

## Что входит в MVP 0.3.1-alpha

### Анализатор

Сохранены возможности основы 0.2.1-alpha:
- поиск `Modules` из корневого каталога игры;
- обнаружение `SubModule.xml`, `Module ID`, версий, DLL, XML, XSLT и ресурсов;
- извлечение зависимостей и деклараций порядка загрузки;
- сопоставление экземпляра BEM и чтение соответствующего `LauncherData.xml`; для остальных установок — поиск профиля Launcher в известных местах;
- поиск отсутствующих зависимостей и объявленных несовместимостей;
- граф ограничений, нарушения и циклы порядка загрузки;
- XML-анализ на уровне отдельных атрибутов;
- XSD unique/key, где доступно;
- инвентаризация XSLT и повторяющихся путей ресурсов;
- Risk Index, Baseline, Candidate Impact;
- HTML- и JSON-отчёты с доказательствами.

Переопределение XML, совпадение пути ресурса или одинаковый метод сами по себе не объявляются доказанным конфликтом. Risk Index — приоритет расследования, а не вероятность вылета.

### Производительность и диагностика сканирования

В 0.3.1-alpha добавлена первая оптимизация файлового обхода: список файлов каждого модуля собирается один раз и повторно используется этапами анализа. Относительный путь XML-файла вычисляется один раз на файл, а не для каждой найденной XML-записи.

HTML- и JSON-отчёты теперь содержат диагностические показатели: время основных этапов, количество обнаруженных файлов, хешированных файлов и разобранных XML/XSLT. Подробно раскрыт общий этап сравнения: отдельно измеряются индексация XML, построение официальной базы, поиск переопределений, попарное сравнение модов, проверка совпадающих путей ресурсов, расчёт рейтинга и подготовка данных отчёта. Дополнительно выводятся счётчики проверенных пар модов и пересекающихся XML-объектов. Эти подэтапы входят в общий таймер сравнения и не должны суммироваться с ним повторно. Время `scan_modules` не включает последующую проверку Baseline, ML inference, запись SQLite и экспорт HTML/JSON.

Эти изменения не меняют правила анализа. На одной реальной установке Bannerlord под Windows 11 выполнены три последовательных полных запуска сканирования: ядро `scan_modules` показало 7,51 / 7,58 / 7,58 секунды. Это контрольный результат для одной конфигурации, а не обещание такой же скорости на других компьютерах или сборках из 50–100 модов. Дальнейшая оптимизация производительности приостановлена: к ней вернёмся, только если реальные крупные сборки покажут неприемлемое время ожидания.

Проверка совпадающих путей ресурсов сначала сравнивает размеры файлов. Разные размеры являются достаточным доказательством различия содержимого, поэтому такие файлы не читаются повторно ради SHA-256. Для файлов одинакового размера выполняется полный SHA-256, чтобы не пропустить изменения с сохранённым размером. В отчёте отдельно показываются число захешированных ресурсов, объём данных, пути с разными размерами и файлы, для которых хеширование удалось пропустить. Постоянный кэш хешей между запусками пока не используется.

Три последовательных отчёта одной установки Bannerlord под Windows 11 показали:

|---|---:|
| Активных / обнаруженных модулей | 12 / 12 |
| Найденных диагностик | 21 во всех трёх отчётах |
| XML-записей | 185 664 |
| Обнаружено файлов | 14 230 |
| Хешировано файлов при инвентаризации | 5 350 (253,7 МБ) |

Проверка 16 совпадающих путей ресурсов выявила 14 путей с разными размерами (28 файлов не потребовали SHA-256); четыре файла с одинаковыми размерами были проверены SHA-256, суммарно около 0,3 МБ. Все три отчёта сохранили одинаковое количество находок.

Таймер `scan_modules` не включает последующие Baseline, ML inference, запись SQLite и экспорт HTML/JSON. В этой установке попарное XML-сравнение сторонних модов фактически не выполнялось: отчёты показывают ноль сторонних XML-записей и ноль сравнений общих объектов. Поэтому качество нового XML-индекса на реальных пересечениях ещё предстоит проверить на сборке, где такие пересечения действительно есть.

Эти данные характеризуют только проверенную установку. Реальные сборки из 50–100 модов пока не тестировались; постоянный кэш хешей между запусками не реализован.

### Локальная база отчётов

Каждое полное сканирование автоматически записывается в SQLite. Сохраняются:
- исходный JSON отчёта;
- версия BCI и отметка времени;
- подпись состава сборки по Module ID, версиям, отпечаткам файлов и порядку;
- число модулей и находок;
- результат проверенного игрового сценария, если пользователь его размечает.

Путь данных Windows: `%LOCALAPPDATA%\BCI\`.

Игровые HTML/JSON отчёты отдельно остаются в `BCI_Reports` внутри каталога игры. Удаление приложения не удаляет пользовательскую базу и модели.

### Разметка результата теста

Во вкладке **«База и обучение»** выбери отчёт и укажи:
- «Тест пройден без регрессии»;
- «Воспроизводимый вылет или функциональная регрессия»;
- сценарий: запуск, загрузка сохранения, новая кампания, карта кампании, обычное сражение, морское сражение или другое;
- заметку о том, что именно проверялось.

Размечай только реальные тесты. Для подтверждения регрессии предпочтителен контролируемый A/B/A: базовая сборка → изменённая сборка → исходная сборка повторно. Неиспытанные отчёты остаются неразмеченными и не попадают в обучение.

Одинаковая подпись сборки и сценарий не раздувают выборку повторными отчётами. Конфликтующие метки одной и той же комбинации исключаются из обучения.

### Локальная модель и обучение

В приложение встроен runtime LightGBM и локальный обучающий контур. Вкладка **«База и обучение»** позволяет обучить модель на отчётах и подтверждённых тестовых результатах. Минимальные условия текущего прототипа: 16 независимых размеченных примеров, не менее 5 каждого класса и не менее 6 разных сборок; дополнительно требуется сформировать контрольную выборку с разделением по подписи сборки.

Текущая ML-задача узкая: оценивать результат тестового сценария для **сборки в целом**. Это не атрибуция первопричины и не определение виновного мода. Предсказание работает в `SHADOW`-режиме: оно выводится отдельно, не меняет Risk Index и не изменяет рекомендации.

**В чистой установке нет заранее обученного на реальных Bannerlord-данных классификатора.** У нас пока нет проверенного набора размеченных примеров, и создавать видимость такой точности на синтетике было бы нечестно. С первого дня поставляются анализатор, базовые экспертные правила, LightGBM runtime и функция локального обучения. Первая ML-модель появляется после накопления и проверки реальных результатов.

### Обновление ML-модели без переустановки

Вкладка содержит действия:
- **Экспортировать модель** — сформировать проверяемый `.bci-model.zip`;
- **Импортировать модель** — установить пакет в профиль пользователя.

При импорте BCI проверяет состав архива, схему признаков, SHA-256 и возможность загрузить модель. Файл помещается в отдельный каталог версии, после чего эта версия становится активной. Приложение, база отчётов и настройки не переустанавливаются. Предыдущие файлы моделей остаются в каталоге для возможности последующей реализации отката.

Пакет предназначен для совместимой версии BCI. Если меняется схема признаков, модель старого формата отклоняется и сначала требуется обновить приложение.

## Где хранятся данные

- SQLite: `%LOCALAPPDATA%\BCI\bci.db`
- Модели: `%LOCALAPPDATA%\BCI\Models\<model-version>\`
- HTML/JSON отчёты: `<Bannerlord>\BCI_Reports\`
- Baseline: `%LOCALAPPDATA%\BCI\profiles\...` (существующий путь Baseline может зависеть от версии профиля)

BCI работает локально. Автоматическая телеметрия и отправка отчётов не реализованы.

## Сборка единого установщика (для разработчика)

Сборка выполняется на **Windows x64**:
Для локальной разработки Windows-сборки: установить Python 3.12 x64 (предпочтительно) или Python 3.13 x64 и Inno Setup 6. Затем `build_windows_exe.bat` создаёт `dist\BCI\`, а `build_windows_installer.bat` запускает тесты, PyInstaller и Inno Setup.

Для получения официального установщика без установки Python на компьютере разработчика используйте `publish_source_branch.bat`: он отправляет подтверждённые исходники в отдельную ветку GitHub, после чего GitHub Actions собирает Windows x64 installer на удалённом Windows Runner с Python 3.12. Подробности — в `FIRST_WINDOWS_BUILD_RU.md`.

Оба сценария используют отдельное виртуальное окружение `.build-venv-3.12` или `.build-venv-3.13` и фиксированные runtime-зависимости. При запуске двойным щелчком консоль остаётся открытой до нажатия клавиши, поэтому сообщение об успехе или ошибке не исчезает. Python 3.12 выбирается первым; если он отсутствует, используется 64-битный Python 3.13. Наличие runtime проверяется по специальному выводу реально запущенного интерпретатора, а не только по коду возврата Python Launcher. Сценарий установщика дополнительно загружает официальный Microsoft Visual C++ Redistributable с `aka.ms` и упаковывает папку `dist\BCI` в EXE. Установщик устанавливает приложение в Program Files и создаёт ярлыки. Проверка этих Windows-сценариев требует запуска на Windows x64; из Linux настоящий Windows EXE собрать и проверить нельзя.

В проект включён workflow `.github/workflows/windows-installer.yml`: после публикации исходников в отдельную ветку он запускает Windows CI и сохраняет build artifact; после push тега `v<APP_VERSION>` выполняет публикацию GitHub Release. Перед первым тегом требуется проверить успешный branch build и вручную просмотреть артефакты. Текущий публичный репозиторий пока не содержит эти исходники: ветка `build/bci-update-system` создана отдельно, а синхронизация исходников выполняется скриптом `publish_source_branch.bat` с явным подтверждением. На этапе сборки официальный VC++ runtime загружается с Microsoft `aka.ms`; для распространения redistributable необходимо соблюдать условия Microsoft.

## Проверки

Локально:

```powershell
python -m unittest discover -s tests -v
```

На момент этой сборки тесты анализатора и локального цикла «отчёт → метка → обучение → экспорт модели → импорт модели → inference» проходят в текущей среде. Перед релизом нужно дополнительно проверить именно Windows-сборку установщика и запуск на чистой Windows 10/11 x64.

## Известные ограничения

- DLL/IL, Harmony patch order, runtime exceptions, crash dumps, SaveableTypeDefiner и глубокая совместимость War Sails ещё не анализируются.
- XSLT инвентаризируется, но не исполняется в полном игровом merge pipeline.
- Интеграционная проверка определения профиля BEM на реальной Windows-установке ещё не выполнена; при неполных данных состояние активности показывается как неизвестное.
- Модель обучается на уровне «сборка + сценарий теста», а не на уровне виновного мода. Для причинной атрибуции потребуется отдельный набор A/B/A-разметки по модам/парам и расширенный движок.
- Если правила не фиксируют взаимное положение пары модов, нейтральный порядок внутри группы пока используется только для воспроизводимости списка; это не означает, что алфавитный порядок оптимален.
- Статическое файловое пересечение не определяет автоматически, какой из двух модов должен победить при перезаписи. Направление нужно подтвердить документацией, авторским патчем или игровым A/B-тестом.
- Текстовый экспорт предназначен для ручного переноса в Vortex; прямого импорта порядка в Vortex и автоматической записи в его профиль нет.
- Метрики на маленькой локальной выборке нестабильны; ML-оценка экспериментальная, не калиброванная вероятность.
- Обновления приложения выполняются через Update Manager и официальный GitHub Releases для установленной версии BCI 0.5.2-alpha и новее. Импорт/экспорт пакета ML-модели остаётся отдельным механизмом.

## Принципы

1. Локальные данные не отправляются без явного действия пользователя.
2. Не запускать DLL модов ради статического анализа.
3. Не считать override доказанным конфликтом.
4. Не выдавать вероятность вылета без эмпирической калибровки.
5. Не удалять и не менять файлы игры/профиля автоматически.
6. Отделять наблюдение, подтверждённую регрессию, триггер и первопричину.
