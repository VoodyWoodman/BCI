## Что реализовано

### Анализ
- Инвентаризация Module/SubModule, XML/XSLT/DLL/resources.
- Зависимости, несовместимости и граф ограничений порядка загрузки.
- XML изменения на уровне атрибутов и XSD ключи.
- Resource/XSLT inventory.
- Baseline, Candidate Impact, Risk Index, evidence-backed HTML/JSON отчёты.

### Накопление данных
- Автоматическая запись каждого скана в SQLite.
- Хранение точной подписи сборки и исходного JSON отчёта.
- Ручные метки успешного/регрессионного теста, сценарий и заметка.
- Отчёты без игровой проверки остаются неразмеченными.
- Повторные отчёты той же подписи сборки и сценария не создают независимые примеры; конфликтующие метки исключаются.

### ML
- LightGBM runtime встроен в Windows application bundle.
- Локальное обучение по накопленным отчётам, без облака.
- Train/holdout split на уровне подписи сборки, чтобы одна и та же конфигурация не попала одновременно в train и test.
- Отдельные метрики precision/recall/F1/accuracy/AUC и число ошибок на контрольной выборке.
- Shadow prediction для всей сборки и выбранного сценария; не влияет на основной рейтинг.
- Версионирование и локальный пакетный импорт/экспорт модели.

## Продуктовые определения

- **Conflict** — подтверждённое негативное взаимодействие, а не просто совпадение файлов.
- **Override** — изменение данных, которое может быть корректным и намеренным.
- **Risk Index** — приоритет расследования 0–100, не вероятность вылета.
- **Evidence Confidence** — качество доказательств вывода.
- **Test Coverage** — проверенные сценарии и комбинации.
- **Regression Trigger** — компонент, включение которого в контролируемом повторяемом тесте вызывает регрессию.
- **Root Cause** — доказанная первопричина; не приравнивать к Regression Trigger без дополнительных доказательств.

## Текущий контрольный статус

Производительность зафиксирована как контрольная точка для одной пользовательской установки, но не считается доказанной для больших сборок. Дальнейшее ускорение не является самостоятельной целью: оно допускается только при сохранении полноты и точности анализа, с регрессионными тестами и измеримым эффектом на реальной рабочей нагрузке. Следующий приоритет — QA и качество доказательств: проверка реальных XML-пересечений, профиля BEM/активности модулей, ложных срабатываний и воспроизводимости находок.

## Обязательные инженерные правила

1. Не объявлять простой override конфликтом.
2. Не выдавать вероятность краша только по статическим пересечениям.
3. Каждый вывод должен иметь evidence.
4. Не рекомендовать удалять обязательные библиотеки из-за большого числа связей.
5. Ранжировать одиночные модули и минимальные конфликтующие группы.
6. Отделять Regression Trigger от Root Cause.
7. Не менять профиль/файлы игры без резервной копии и явного подтверждения.
8. Не исполнять DLL модов ради статического анализа.
9. При недостатке данных сообщать `Insufficient evidence`.
10. Привязывать тесты к хешам модов, версии игры, DLC, load order, настройкам и сценарию.
11. Модель в MVP не влияет на основной Risk Index.

## Критерии качества

- Precision / Recall.
- False Positive / False Negative rate.
- Pairwise / N-way interaction coverage.
- Калибровка вероятностных оценок: Brier Score/reliability curve.
- Воспроизводимость регрессии.
- Доля отчётов с полным evidence trail.
